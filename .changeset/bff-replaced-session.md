**BFF: a refresh still in flight can no longer put a replaced or logged-out session back.** The browser keeps whichever `Set-Cookie` arrives last. A request that was already out when someone signed in or logged out — an app-API call renewing an expired token, a page render, another tab's restore — refreshed the OLD sealed session and re-sealed it on the way back. After a login that put the previous account back under the new one; after a logout it re-created the cookie logout had just cleared. The browser tab can hold back its own refreshes, but not these.

Each sign-in now gives the sealed session a new id, and a sign-in or logout records the id it replaced for ten minutes. Every path that re-seals after a refresh — `/api/_lukk/refresh`, the auth proxy's 401 retry, the app-API proxy's proactive refresh, SSR hydration, and a step-up confirmation — checks it before rotating and again as late as it can — after the upstream body has been read, right after the user loads during a render, and once more before the render's headers go out — withholding the session cookie if the session ended meanwhile. With Nuxt 4's opt-in `experimental.ssrStreaming` the render hooks run after the response has started, so there the check right after the user load is the last one: a session that ends between that point and the first streamed chunk is not caught. A page render for a replaced session renders signed out and unresolved rather than as that account, so the client restores with the cookie the browser now holds — including when the render throws. `/api/_lukk/refresh` answers `409` for a replaced session, and so does a step-up confirmation captured for one (the confirmation belonged to that session and isn't stored); a restoring tab waits a moment and asks once more (the browser most likely holds the newer cookie by then), treating a second `409` as signed out rather than "couldn't tell", and a tab that was already signed in reloads its user so it stops showing the previous account. A restore retry answered "no session" now also clears a user still on screen.

With SSR hydration on (the default), a render for any request carrying a real session is now `no-store`, including one that ends up not hydrating because that session was replaced: components that fetch during SSR without gating on `ready` still render its data. With `ssrHydrate: false` the hydration plugin isn't registered, so this doesn't apply — mark such renders `no-store` yourself.

A logout from a session a sign-in has already replaced no longer clears the cookie: that cookie belongs to the newer session, and clearing it signed that session out in the browser while leaving it alive on lukk. And when the proxy drops a rotation it has already made (the session was replaced while the refresh was out), it logs those new tokens out in the background — otherwise a browser still holding the old cookie replayed a consumed refresh token later, and lukk's reuse detection revoked the family and reported a theft that never happened. A console warning fires once if more than 50,000 sessions are replaced within ten minutes and the oldest stop being guarded.

**Logout clears the sealed session only once the session is over** — lukk answered `2xx`, or rejected credentials that can't be renewed. A throttled logout (`429`), an upstream outage, or a `401` whose refresh merely failed used to clear the cookie anyway, leaving the session live on lukk with nothing pointing at it while the visitor believed they had logged out. The status now reaches the client, which can retry.

**Logout presents the session's refresh token to lukk** as well as the access token, so a lukk release that accepts it can end the session even when the access token has expired and refreshing is throttled or failing — without spending a rotation first. Older releases ignore it.

**The proxy no longer reuses a refresh token that lukk's response didn't include.** A sign-in without one fell back to the refresh token of the session being replaced, and a rotation without one kept the token lukk had just consumed: the first turned the browser back into the previous account at the next refresh, the second replayed a consumed token into a false theft report. Without a refresh token the session now simply ends when its access token does. lukk always returns one in body mode; this only matters for a cookie-mode upstream or a rebound `LoginResponse`. And a logout from a replaced session still renews its expired token and sends an authenticated `/logout`, so lukk revokes that session instead of leaving it alive — only the result is never written back.

Each sign-in adds the id to the sealed session — about 45 bytes of JSON, more once sealed — worth knowing if yours is already near the 4 KB cookie limit.

Also fixed on the way:

- **The server-side refresh single-flight is keyed by the session's own id**, not h3's. A sign-in re-seals the new session under the old h3 id, so a refresh for it could join one still out for the session it replaced — and seal that session's tokens under the new one.
- **SSR hydration and the proxies now share one single-flight.** Nitro's handlers and the Nuxt app's server bundle each carry their own copy of the module, so a page render and a proxy refreshing the same session at once each rotated the token. Both registries now live on `globalThis`.

Limits: what remains is the time between a response's headers leaving the server and the browser storing them. The record is per server process, like the single-flight — behind a load balancer without sticky sessions, a request another instance serves isn't covered, and on serverless or edge runtimes a process is an instance or isolate, so the guard is best-effort there. A replaced session's token can still be rotated by a refresh that was already out; it is never written back, and those new tokens are logged out in the background. A session sealed before this version has no id of its own and is recorded by h3's; that covers every refresh and re-seal, but a page load that needs no refresh can still render such a session as the account it replaced until the tab reloads (no cookie is written). After a sign-in whose response never reached the browser, the session it replaced reads as signed out for those ten minutes — but it is still live on the server until it is logged out or expires, and requests with its cookie keep working until its access token expires.
